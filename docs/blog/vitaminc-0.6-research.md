# Vitamin C 0.6 announcement research

Investigated on 17 October 2026. The comparison is `vitaminc-v0.5.1..vitaminc-v0.6.0`, covering the per-crate changelogs, recent merges, ADR 0001, current implementations, examples, conformance tests and CI configuration. The working tree's tracked contents matched the 0.6.0 tag when inspected. GitHub's API confirmed publication of the facade, AEAD, normalize and ORE releases that day; the facade release was published at 04:49:15 UTC. The web search index did not yet expose the new release, so the draft relies on tagged repository sources and GitHub release records.

The editorial angle is **shared security foundations let applications reuse the effort invested in their design, testing and scrutiny**. The opening follows Dan's argument that this matters increasingly as coding agents build on open source libraries. It makes no numerical claim about agent adoption or security outcomes. Vitamin C's MIT license supports the invitation to use, inspect, modify and build on the code; see [LICENSE](../../LICENSE). Expert vetting is presented as a design goal and ongoing responsibility, with concrete testing evidence, rather than a claim of a completed independent audit.

The shared data model for encryption and indexing is the main 0.6 example of that broader purpose, grounded in ADR 0001. Centralizing type and container rules gives implementations fewer places to diverge. The intended reader is a developer building software that handles sensitive data, with or without coding agents. The draft uses CipherStash's first-person voice and Dan Draper's byline, consistent with the repository authorship, and remains an unpublished draft.

The facade changelog is too narrow to represent the milestone on its own. Most of the changes live in the AEAD, encrypt, normalize, ORE and Node crates.

The broader project story predates 0.6. `Protected<T>`, explicit access to secrets, redacted debugging, timing-safe comparison, random generation, AES-256-GCM, structured PRFs, canonical contexts and AWS KMS-backed HMAC are existing capabilities. `Locked<T>` also predates this release. These explain why Vitamin C is useful but should not be presented as inventions of 0.6. Sources: [protected](../../packages/protected/README.md), [random](../../packages/random/README.md), [encrypt](../../packages/encrypt/README.md), [context](../../packages/context/README.md), [HMAC](../../packages/hmac/README.md), [KMS](../../packages/kms/README.md).

Points to preserve when editing the announcement:

- **This is a breaking data migration.** New leaves use wire version 2. The old Rust `Encrypt`/derive path wrote untagged version 1 plaintext and requires decrypting with 0.5 and re-encrypting with 0.6. `opening_version_1()` is only appropriate for already tagged leaves from the old `Value` path; applying it to untagged data can silently return the wrong value. Old `LeafTypeAad` contexts also changed, and host/guest transport frames must be upgraded together. See [encrypt migration notes](../../packages/encrypt/CHANGELOG.md) and [frame notes](../../packages/aead-frame/CHANGELOG.md).
- **Index normalization is not ciphertext normalization.** Matching timestamp terms use microsecond precision even when ciphertext retains finer precision. Integer and float domains differ. Text equality uses Unicode 16 NFC without case or accent folding; text order terms fold both. Booleans, null and undefined have no equality or order term. Unknown logical types stop index collection instead of silently leaving gaps.
- **Existing primitive PRF inputs retain their old domains.** Their outputs are unchanged, but they do not match the new normalized domains. Writes and queries must use the same input API, key and context. Collecting a document's normalized terms does not automatically choose an index context for each field; the caller uses the term paths to do that.
- **Order terms expose order, and equality terms expose equality.** Combining indexes combines their leakage. `vitaminc-ore` supplies the encoding and integration layer. It does not itself provide a database or a concrete encryption scheme. Cross-column terms are not generally comparable, and scheme support varies by target.
- **Structured encryption has a specific authentication contract.** Map keys and container shape remain visible. Sequence elements are bound to their sequence, but neither their index nor the sequence length is authenticated. Passthrough fields are unencrypted and unauthenticated. Do not generalize leaf authentication into a claim that every document edit is detected.
- **Bindings have different maturity and guarantees.** The Node crate is an addon-building library, not a standalone npm SDK. Its decrypted integers now always become `BigInt`. Go remains an unpublished WASI spike. Rust cannot guarantee wiping copies held by a JavaScript or Go runtime. Host projections are explicit in the conformance corpus; avoid promising identical host values or universally identical re-encodings.
- **Verification claims need a scope.** Kani covers bounded `Locked` layout/wipe invariants. Miri and sanitizers target protected-memory code; other checks include known-answer vectors, property tests, mutation testing and differential fuzzing. These do not establish that the entire suite is formally verified, independently audited, or FIPS certified. No such blanket claim is made in the draft.
- **Compatibility is partly a goal.** Native and WASM encryption backends exist. `no_std` remains an aspiration; no crate currently provides it, according to the repository guidelines. Rust minimums are 1.88 generally and 1.94.1 for `vitaminc-kms`/`aws-kms`.
- **Avoid unsupported performance claims.** Shared traversal removes duplicate work structurally, and batching permits fewer calls. The release research did not establish a measured speedup. Planning also holds protected plaintext leaves together before sealing, so memory grows with document size.

Some documentation needs care as a source. ADR 0001 uses the interim trait name `Plaintext`; the released name is `Encrypt`. The encrypt README still has old installation versions and some broad security language. The Go overview includes an old statement about untagged static Rust encryption that the new data model supersedes. The draft follows the 0.6 changelogs and implementation where these differ.

The draft's example was compiled and executed against local 0.6.0 sources in an isolated temporary Cargo project, using the exact facade features shown in the article. It generated separate random AES and HMAC keys, encrypted a protected `i64`, asserted that an `i8` query produced the same normalized keyed term, and decrypted back into `Protected<i64>`. This checks the article example; it is not a fresh run of the project's entire verification suite. The Mermaid diagram describes that example's flow and labels normalized plaintext separately from keyed index output.
